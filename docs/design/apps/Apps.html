The idea: an app is a saved visual plus a short list of where its data comes from. Piopio reads those sources and hands the result to the page. The page stays offline, so data only flows in.

A

From a visual to an app

Click through, or use the steps
  • Keep is the one new button on a visual card. A visual is still a snapshot; Keep turns it into an app: Piopio rewrites it to read its data instead of carrying it, saves it as a file in the project, lists it in the Library and (unless you untick it) pins it there.
  • An app is a page in the content card: the app at full width, Piopio's toolbar above it (Updated, Refresh, Sources, ⊘ offline), and a conversation about it on the right, closed by default after the first time.
  • Changing it is asking. The model edits the file; the page reloads; the change is a checkpoint like any other edit (Undo).
  • Refreshing costs nothing. Reading a file, a connector or Piopio's numbers runs no model. Only changing the app does.
B

The Library

Everything Piopio and your agents made, in one place; a mockup selected
  • An index, not a store. Every item is a file where it already lives: a project's folder, a conversation's folder, an agent's files/, ~/Piopio/Apps/. Git, checkpoints and Finder keep working (25 VS3 holds). Remove from Library hides it; deleting the file is a separate, confirmed step.
  • What's in it, on its own: files Piopio or an agent wrote that are things to look at (pages and mockups, documents, spreadsheets and CSVs, images, slides) and apps. Code isn't: a Build session's .swift files stay in Build. Visuals still in a conversation show too, marked, with Keep. Any other file can be added from its ⋯ menu.
  • Each item says where it came from: the conversation that made it (a link back), who (Piopio or an agent), and when. Piopio writes a one-line note when it makes a file, as agents already do with note_file (06 §14), so search finds "the gas comparison".
  • Pin puts an item on the shelf at the top and under Library in the sidebar (the five most recent pins; the rest stay on the shelf). Any item can be pinned; apps are the usual ones. The sidebar's Pinned section stays for conversations and agents.
  • Filters: kind (All, Apps, Documents, Pages, Visuals, Images, Data), place (a project, an agent, conversations) and search. ⌘K finds items too.

F

Under the hood

One file; data in, your click out
<!-- household/apps/spending.html -->
<script type="application/json" id="piopio-app">
{
  "title": "Spending",
  "sources": {
    "expenses": { "file": "data/expenses.csv" }
  },
  "refresh": { "onOpen": true, "onChange": true }
}
</script>

<div id="chart"></div>
<script type="module">
  import { Chart } from "piopio-lib://chart.js";
  // Called on every refresh with what Piopio read.
  piopio.onData(({ expenses, updatedAt }) => {
    draw(byMonth(expenses));
  });
  // Buttons still only send words, on a click.
  pay.onclick = () => piopio.prefill("Ask Rita to pay…");
</script>

// Other source kinds
{ "tool":   "calendar_list_events", "args": { "days": 7 } }
{ "script": "bills.js", "tools": ["gmail_search"] }
{ "piopio": "stats.spend", "args": { "by": "agent" } }
  • The manifest is the contract. Sources and refresh live in one JSON block at the top of the file. Allowing an app means allowing exactly that list; a different list asks again.
  • The engine reads, the app draws (25 VS4 again). Results are cached in Piopio's data folder, not the project, so an app opens instantly with its last data and a phone can draw it too.
  • The sandbox doesn't change (25 §5): no network, no files. What's new is piopio.onData, one way in. That's why the worst an app can do is still look wrong.
